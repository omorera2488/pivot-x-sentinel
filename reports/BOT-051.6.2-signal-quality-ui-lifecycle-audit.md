## 1. Executive summary

El ticket `351931195` no muestra Signal Quality (ni abierto ni cerrado) porque **nunca se persistió** — no es un bug de lookup, de join de IDs, ni de renderizado. La causa raíz es un **bug real de serialización JSON** introducido en `BOT-051.5` (commit `23101dd`) y activo en producción desde el reinicio del proceso de hoy (`2026-09-23T13:23:55Z`): `strategy/signal_quality.py::_replay_armado_origin()` puede devolver un `numpy.bool` (en vez de `bool` nativo de Python) para `senal_venta_at_last_bar`/`senal_compra_at_last_bar`, que se propaga a través de una cadena `and`/`or` hacia `diagnostics["structure_replay_matches_signal"]`. `json.dumps()` **nunca** puede serializar `numpy.bool` (confirmado empíricamente, siempre falla con el mismo mensaje) — esto revienta `score_store.record()` **DESPUÉS** de que la orden ya fue colocada (comportamiento de trading no afectado) pero **ANTES** de escribir la línea al archivo, así que no queda ni rastro (ni siquiera una línea corrupta).

El log real del bot en vivo (obtenido vía `GET /events`, proceso corriendo ahora mismo) muestra el error EXACTO, dos veces, para las dos únicas señales reales ocurridas desde el reinicio de hoy: `351931195` (14:35 UTC, cerrada SL a las 15:49 UTC) y `352047367` (16:20 UTC, **todavía abierta ahora mismo** con el mismo problema). Esto significa que el bug es **actualmente activo** y afectará a **toda** señal futura donde la ventana de replay de Structure confirme la señal (el caso normal/exitoso, no un edge case raro).

`351437683` (el ticket de comparación, que SÍ funciona) fue persistido por el proceso ANTERIOR al reinicio de hoy — uno de vintage `BOT-051.4` (sin `signal_quality_diagnostics`, sin `provenance`) que nunca intentó serializar ese campo, por eso nunca pisó el bug.

`BOT-051.6.1` **no causó** el problema — el código que revienta (`bot.py`/`score_store.py`/`signal_quality.py`) es idéntico desde `BOT-051.5`, `BOT-051.6.1` solo tocó `panel/`. Lo que sí hizo `BOT-051.6`/`BOT-051.6.1` es hacer **visible** en el panel un hueco de persistencia que antes era invisible (porque Signal Quality solo se mostraba en operaciones cerradas, y porque el popover legacy rellenaba el ícono con la calificación aunque `signal_quality` faltara).

## 5. Frontend behavior

Código real de `panel/app.js::scoreBadge()` (sin cambios desde `BOT-051.6.1`):

```js
function scoreBadge(scoresMap, ticket) {
  const s = scoresMap && scoresMap[ticket];
  if (!s || !s.signal_quality) return "";
  return `
    <span class="score-badge">
      <span class="score-icon" tabindex="0">ⓘ</span>
      <div class="score-pop">
        ${signalQualitySection(s.signal_quality, s.signal_quality_diagnostics)}
      </div>
    </span>`;
}
```

**Confirmado explícitamente (no rechazado):** `if (!signal_quality) → no badge`. Si `s.signal_quality` existe, se renderiza el ícono + popover con `signalQualitySection(s.signal_quality, s.signal_quality_diagnostics)`. Si `s` no existe en el mapa (el ticket ni siquiera tiene una línea en `score_store`) o existe pero `s.signal_quality` es `null`/`undefined` (registro legacy o con solo `score`), la función devuelve `""` — ningún ícono, ningún fallback, ningún placeholder. Esto es **exactamente** lo que le pasó a `351931195`: no está en `scoresMap` en absoluto (ver sección 9/10).

`signalQualitySection()` recibe el vector completo (`Momentum`/`Alignment`/`Structure`/`Context`/`Direction`) y el dict de `diagnostics` (para las razones de `UNAVAILABLE`) — sin cambios desde `BOT-051.6.1`, no aplica a este caso porque nunca se llega a invocar (el `if` de arriba corta antes).

## 15. Root cause

**Bug de serialización JSON, no de identidad ni de lookup.**

`strategy/signal_quality.py::_replay_armado_origin()` (líneas 296-300):

```python
down = close[i - 1] >= ema_line[i - 1] and close[i] < ema_line[i]   # numpy.bool (arrays numpy)
up = close[i - 1] <= ema_line[i - 1] and close[i] > ema_line[i]     # numpy.bool
...
senal_venta = armado_venta and down   # si armado_venta (python bool) es True, "and" devuelve `down` TAL CUAL -> numpy.bool
senal_compra = armado_compra and up   # idem
```

Y en `compute_signal_quality_at_bar()` (líneas 367-370):

```python
replay_matches = (
    (direction < 0 and replay["senal_venta_at_last_bar"]) or
    (direction > 0 and replay["senal_compra_at_last_bar"])
)
```

Cuando la ventana de replay SÍ confirma la señal real (el caso normal y esperado para una señal que efectivamente dispara — exactamente lo que pasó en ambos tickets), el operando ganador de la cadena `and`/`or` es el valor `numpy.bool` sin convertir, y ese tipo se propaga hacia `replay_matches`, luego hacia `diagnostics["structure_replay_matches_signal"]` (línea 414-419), que viaja intacto hasta `execution/src/bot.py::process_closed_bar()` como parte de `sq_diagnostics`, pasado a `score_store.record(..., signal_quality_diagnostics=sq_diagnostics)`.

**Verificado empíricamente en esta auditoría** (numpy 2.2.6, el mismo que usa el proyecto): `json.dumps()` **siempre** falla sobre CUALQUIER valor `numpy.bool` (`True` o `False`), con el mensaje EXACTO `TypeError: Object of type bool is not JSON serializable` — idéntico, carácter por carácter, al que aparece en el log real de producción dos veces.

`FactorObservation`/`SignalQualityVectorV1.to_dict()` (el vector en sí) **no tiene este problema** — sus valores numéricos pasan explícitamente por `float(raw_value)` (línea 136) antes de guardarse, por eso `momentum`/`structure` de tickets anteriores serializan bien. El bug está **aislado** al campo `structure_replay_matches_signal` dentro de `diagnostics`, que no pasa por esa misma disciplina de casteo (se agregó en `BOT-051.5` como un dict "ligero" de telemetría, sin el mismo blindaje de tipos que `FactorObservation`).

`score_store.record()` arma el diccionario completo y recién AL FINAL llama a `json.dumps(row, ...)` **antes** de escribir cualquier byte al archivo — por eso no queda ni una línea corrupta: la excepción ocurre mientras se evalúa el argumento de `f.write()`, así que `f.write()` nunca se ejecuta.

La excepción no está atrapada en ningún punto entre `score_store.record()` y el loop externo de `run()` — se propaga hasta el `except Exception` genérico de `run()`, que loguea "Error en el ciclo" y fuerza una reconexión con backoff.

## 16. Classification / severity

```text
Clasificación: PERSISTENCE_FAILURE
```

(No es `IDENTITY_LINKAGE_FAILURE` -- sección 10 descarta explícitamente cualquier diferencia de topología de IDs. No es `API_JOIN_FAILURE` ni `FRONTEND_LOOKUP_FAILURE` -- secciones 5/14 confirman que backend y frontend hacen exactamente lo que deben con el dato que SÍ existe; el problema es que el dato nunca llegó a existir. Tampoco es `RUNTIME_VERSION_MISMATCH` como causa raíz -- aunque hay evidencia de que el runtime SÍ cambió recientemente (sección 12), el bug en sí es un defecto de código presente en el commit actual, no una discrepancia entre versiones corriendo.)

```text
Severidad: DATA_CAPTURE_GAP + OOS_EVIDENCE_RISK
```

- `DATA_CAPTURE_GAP`: cada señal real futura donde Structure replay confirme la señal (el caso esperado) perderá su snapshot de Signal Quality por completo -- no solo `structure_replay_matches_signal`, **todo el registro** (incluyendo `score` legacy, que también iba en la misma línea).
- `OOS_EVIDENCE_RISK`: esto ataca directamente la acumulación de `BOT-051.5`/`BOT-051.7` -- mientras el bug siga activo, **ninguna LIMIT nueva exitosa** (con replay confirmado) sumará evidencia al dataset OOS, deteniendo de facto la acumulación real que `BOT-051.6`/`BOT-051.6.1` asumían continua.
- **NO es** `TRADING_BEHAVIOR_RISK` en el sentido de entradas/SL/TP/sizing incorrectos: `_place_order()` corre ANTES del crash y con los mismos argumentos de siempre (verificado: `sl`/`tp`/`entry` de ambos tickets son coherentes con lo que loguea `_place_order()`, sin señales de corrupción). Sí se identificó un **riesgo secundario, no confirmado como dañino en este incidente** (ver sección 17) sobre el reprocesamiento de la misma barra tras la excepción.

## 17. Whether BOT-051.6.1 caused or exposed it

```text
Caused: NO
Exposed: SI
```

El código que falla (`_replay_armado_origin()`, `compute_signal_quality_at_bar()`, `process_closed_bar()`, `score_store.record()`) es **idéntico** desde el commit de `BOT-051.5` (`23101dd`, 2026-09-22) -- `BOT-051.6` y `BOT-051.6.1` no tocaron `strategy/signal_quality.py`, `execution/src/bot.py` ni `execution/src/score_store.py` (lado de escritura) en absoluto (confirmado con `git diff` de esos commits contra `HEAD`, cero cambios en esos archivos desde `23101dd`).

Lo que `BOT-051.6.1` sí hizo fue **eliminar el fallback visual legacy** del popover (`scoreBadge()` ya no muestra Divergencia/Tendencia/CVP/Nodo cuando `signal_quality` falta) y `BOT-051.6` hizo que Signal Quality se muestre desde que nace la LIMIT (no solo al cerrar). **Antes de `BOT-051.6`**, un ticket sin `signal_quality` habría mostrado igual el ícono con la calificación legacy (si `entry_score` existía) -- en este incidente específico, `entry_score` **tampoco llegó a persistirse** (la excepción interrumpió `record()` antes de escribir la línea completa, que incluía tanto `score` como `signal_quality`), así que **incluso con el popover legacy de antes de `BOT-051.6.1`, este ticket en particular habría quedado igual de vacío** -- el fallback legacy no habría salvado este caso puntual, porque el problema es de PERSISTENCIA total, no de qué campo mostrar. Confirmado, no asumido: se revisó `score_store.record()` y el `if` que la gatilla -- ambos campos (`score` y `signal_quality`) viajan en el MISMO `row` y el MISMO `json.dumps()` que revienta.

## 18. Recommended fix design (NO implementado)

**Prioriza la alternativa menos invasiva, preserva snapshot t0 inmutable, lifecycle linkage, provenance OOS y behavior invariance -- NO se implementa en esta tarea (audit-only).**

1. **Fix mínimo y directo** (más recomendado): castear explícitamente a `bool()` nativo de Python en el punto exacto donde se arma `replay_matches` en `strategy/signal_quality.py` (alrededor de la línea 367-370), o directamente en `_replay_armado_origin()` al construir el dict de retorno (línea 311-314) -- envolver `senal_venta`/`senal_compra` en `bool(...)`. Cambio de una línea, no toca ningún contrato congelado (`SignalQualityVectorV1` no se modifica, solo el dict `diagnostics` que ya es explícitamente "no congelado, solo telemetría técnica" según su propio docstring).
2. **Defensa en profundidad adicional (opcional, complementaria)**: en `execution/src/score_store.py::record()`, usar `json.dumps(row, default=lambda o: bool(o) if isinstance(o, np.bool_) else ...)` o simplemente `json.dumps(row, cls=...)` con un encoder que tolere tipos numpy -- protegería contra futuros leaks similares en cualquier campo, no solo este.
3. **Manejo de la excepción con try/except alrededor de `score_store.record()`** en `execution/src/bot.py` (mismo patrón defensivo ya usado para `_compute_signal_quality()`) -- evitaría que un futuro bug de serialización interrumpa el ciclo completo del bot (evita el `Error en el ciclo`/reconexión innecesaria y el riesgo secundario de reprocesar la misma barra, sección 19).
4. **Backfill/migración de tickets ya perdidos**: `351931195` y `352047367` (y cualquier otro futuro hasta que se aplique el fix) **NO tienen Signal Quality recuperable** -- el snapshot de t0 requiere la ventana de velas EXACTA que existía en ese momento causal; reconstruirlo hoy usando `copy_rates_range()` actual **sería una reconstrucción retrospectiva**, no el snapshot real de t0 (violaría el principio de la sección 11 del enunciado de esta auditoría: "no reconstruir retrospectivamente como sustituto"). Si se reconstruye para диagnóstico, debe marcarse explícitamente `RECONSTRUCTED`, nunca presentarse como `PERSISTED LIVE SNAPSHOT`.

## 19. Required future tests

## 21. Limitations

- No se pudo obtener el hash de commit EXACTO cargado por el proceso en vivo (no tiene un endpoint que lo exponga y los tickets fallidos no tienen `provenance` persistido, precisamente porque el bug interrumpe la escritura). La conclusión de la sección 12 es circunstancial (basada en timestamps de arranque de proceso vs. commits), no una confirmación directa.
- No se investigó por qué aparecen 2 PIDs de `uvicorn` con el mismo comando/puerto (sección 12) -- fuera del alcance de este incidente puntual.
- No se determinó con certeza si el proceso ANTERIOR al reinicio de hoy (el que sí persistió `351437683` sin `provenance`/`diagnostics`) era vintage `BOT-051.4` exacto o una variante intermedia -- ambas son consistentes con la evidencia disponible.
- No se verificó exhaustivamente si el reprocesamiento de barra (sección 20) es seguro en TODOS los escenarios posibles, solo en el observado.
- Esta auditoría es de solo lectura por mandato explícito de la tarea -- no se aplicó ni se probó el fix propuesto.
