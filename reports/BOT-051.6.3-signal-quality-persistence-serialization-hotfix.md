# BOT-051.6.3 — Signal Quality Persistence Serialization Hotfix

**Tipo:** `PRODUCTION HOTFIX / PERSISTENCE RELIABILITY`
**Fecha:** 2026-09-23
**Decisión final:** `SIGNAL_QUALITY_PERSISTENCE_HOTFIX_READY`

## 1. Executive summary

Implementa el fix derivado de `BOT-051.6.2` (auditoría read-only): un `numpy.bool_` sin castear en `strategy/signal_quality.py::_replay_armado_origin()` se filtraba, vía la semántica de corto-circuito de `and`/`or` de Python, hasta `diagnostics["structure_replay_matches_signal"]`, y `json.dumps()` **siempre** falla sobre ese tipo — rompiendo `score_store.record()` **después** de colocar la orden real (comportamiento de trading no afectado) pero **antes** de escribir la línea, así que el snapshot de Signal Quality de esa LIMIT se perdía por completo, sin dejar rastro.

Fix aplicado en tres capas, en el orden de prioridad que pide el enunciado:
1. **Productor** (`strategy/signal_quality.py`): `bool(...)` explícito en las tres expresiones donde el tipo se originaba/propagaba (`down`/`up`, `atr_ok`, `replay_matches`).
2. **Tests** que ejercitan el camino real con arrays NumPy (no fixtures ya saneados), forzando específicamente el escenario que faltaba cubrir (`structure_replay_matches_signal == True`).
3. **Defensa en profundidad** (`execution/src/score_store.py`): un normalizador `_json_safe()` explícito y acotado (solo `numpy.bool_`/`numpy.integer`/`numpy.floating`, nunca conversión genérica a texto) + **aislamiento** de `score_store.record()` en `execution/src/bot.py` para que un fallo de persistencia/observabilidad nunca vuelva a tumbar el ciclo principal ni a arriesgar el reprocesamiento de la misma barra.

`strategy/engine.py` y `strategy/live_signal.py` quedan con diff cero. Ningún contrato de `SignalQualityVectorV1` se reabre. `351931195`/`352047367` (las dos LIMITs reales que perdieron su Signal Quality, identificadas en `BOT-051.6.2`) **no se backfillean** como evidencia OOS — quedan documentadas como pérdida permanente, consistente con "nunca reconstruir retrospectivamente como sustituto de un snapshot genuino de t0".

## 3. Root cause inherited from BOT-051.6.2

Ver `reports/BOT-051.6.2-signal-quality-ui-lifecycle-audit.md` para la investigación completa (evidencia de producción: log real del bot vía `GET /events`, dos incidentes idénticos hoy — tickets `351931195` y `352047367` — con el mensaje `TypeError: Object of type bool is not JSON serializable`, exactamente después de "Orden ... colocada" y antes de cualquier log de persistencia). Resumen del mecanismo:

```python
# strategy/signal_quality.py::_replay_armado_origin(), ANTES del fix
down = close[i - 1] >= ema_line[i - 1] and close[i] < ema_line[i]   # numpy.bool_ (arrays numpy)
...
senal_venta = armado_venta and down   # armado_venta es bool nativo; si es True, "and" devuelve `down` TAL CUAL

# compute_signal_quality_at_bar(), ANTES del fix
replay_matches = (
    (direction < 0 and replay["senal_venta_at_last_bar"]) or
    (direction > 0 and replay["senal_compra_at_last_bar"])
)
```

Python `and`/`or` devuelven uno de los OPERANDOS, no un `bool` coercionado — si el operando ganador es un `numpy.bool_`, el resultado también lo es. Esto ocurre precisamente cuando Structure replay **confirma** la señal (`replay_matches == True`), el caso normal/exitoso para una señal real que dispara — no un edge case raro.

## 4. Exact implementation

### 5. Producer type fix

`strategy/signal_quality.py` — tres casts explícitos, en el punto exacto donde cada tipo se origina o se recompone, sin tocar ninguna semántica de Structure/Momentum/Alignment/Context:

```python
# 1) donde nace el numpy.bool_ (comparaciones sobre arrays numpy)
down = bool(close[i - 1] >= ema_line[i - 1] and close[i] < ema_line[i])
up = bool(close[i - 1] <= ema_line[i - 1] and close[i] > ema_line[i])

# 2) atr_ok -- mismo mecanismo (atr_b es numpy.float64), no se serializaba
#    directamente hoy pero se normaliza igual para que ningun uso futuro
#    herede el bug
atr_ok = bool(not math.isnan(atr_b) and atr_b > 0)

# 3) defensa en profundidad en el punto de uso -- la variable que
#    efectivamente viaja a diagnostics["structure_replay_matches_signal"]
replay_matches = bool(
    (direction < 0 and replay["senal_venta_at_last_bar"]) or
    (direction > 0 and replay["senal_compra_at_last_bar"])
)
```

`senal_venta`/`senal_compra` (que ya eran `armado_venta and down` / `armado_compra and up`) quedan automáticamente `bool` nativo porque `armado_venta`/`armado_compra` YA eran `bool` nativo y `down`/`up` ahora también lo son — no hizo falta tocar esas dos líneas.

**No se modificó**: `SignalQualityVectorV1`, `FactorObservation`, ningún threshold/bin/peso, la lógica de armado/origen en sí (solo el TIPO de retorno de una comparación, nunca el VALOR lógico), `Momentum`/`Alignment`/`Context`, `direction` como metadato. Verificado con la suite completa de `strategy/test_signal_quality.py` (25 checks previos, todos siguen pasando sin cambios).

### 6. Persistence isolation

`execution/src/bot.py::process_closed_bar()` — la llamada a `score_store.record()` (después de `_place_order()`) queda envuelta en su propio `try/except`:

```python
ticket = self._place_order(signal.dir, signal.entry, signal.stop, signal.target)
if ticket is not None and (entry_score is not None or signal_quality is not None):
    try:
        score_store.record(...)
    except Exception as e:
        self._log(f"ERROR: no se pudo persistir la calificacion/Signal Quality del ticket "
                  f"#{ticket} ({e!r}) -- la orden ya esta colocada, no se ve afectada.")
```

Esto es **estrictamente posterior** a `_place_order()` — no puede ocultar, revertir ni duplicar un `order_send()`, no toca `ticket`/`sl`/`tp`/volumen, no reintenta la orden. Efecto colateral **deseado y verificado**: `self._last_processed_time = int(r["time"])` (última línea de `process_closed_bar()`) ahora SIEMPRE se alcanza, incluso si la persistencia falla — cerrando el riesgo secundario que `BOT-051.6.2` había identificado (una excepción sin aislar podía dejar la barra "sin marcar como procesada", con riesgo teórico de reprocesamiento). Verificado explícitamente con un test nuevo (sección 8, escenario D).

### 7. Optional serialization defense decision

Evaluado y **sí implementado**, como defensa en profundidad adicional (no como sustituto del fix del productor — ver prioridad explícita del enunciado: 1) productor corrige tipos, 2) tests los detectan, 3) persistencia puede tener defensa adicional).

`execution/src/score_store.py::_json_safe()` — normalizador recursivo, pequeño y explícito:

```python
def _json_safe(value):
    if isinstance(value, dict):
        return {k: _json_safe(v) for k, v in value.items()}
    if isinstance(value, list):
        return [_json_safe(v) for v in value]
    if isinstance(value, np.bool_):
        return bool(value)
    if isinstance(value, np.integer):
        return int(value)
    if isinstance(value, np.floating):
        return float(value)
    return value
```

Aplicado una sola vez, justo antes de `json.dumps()` en `record()`. Decisión documentada explícitamente en el docstring del módulo. **Cumple los 5 requisitos del enunciado**: (a) explícita — solo 3 `isinstance` sobre tipos numpy concretos; (b) pequeña — 13 líneas; (c) con tests (sección 8, escenario H de `test_score_store.py`, usa un `numpy.bool_`/`numpy.int64` REAL, no simulado); (d) soporta solo tipos razonablemente esperables desde `strategy/` (`bool_`/`integer`/`floating`, los tres tipos escalares que un cálculo numérico con arrays numpy puede filtrar) — **no** intenta manejar `numpy.ndarray`, objetos arbitrarios, ni nada fuera de esa lista; (e) **no convierte nada a texto** — cualquier tipo no reconocido se devuelve tal cual y `json.dumps()` sigue fallando fuerte y visible sobre él, en vez de ocultar una estructura inválida.

## 8. Tests added

**Test A — NumPy bool producer** (`strategy/test_signal_quality.py`, secciones D y H):
- Extiende el fixture YA existente de `_replay_armado_origin()` (sección D, arrays numpy reales, armado en bar 10, señal en bar 20) con: `type(senal_venta_at_last_bar) is bool` (no `numpy.bool_`) y `json.dumps(replay)` sin excepción.
- Nueva sección H: recorre `compute_signal_quality_at_bar()` de punta a punta sobre el fixture aleatorio ya existente (seed fija=42, 100% determinista, `strategy/test_signal_quality.py` sección F) variando `b`/`direction` hasta encontrar **al menos un caso real** con `structure_replay_matches_signal == True` (encontrado en `b=168, direction=-1` — determinista, no depende de suerte) y otro con `False` — para CADA uno verifica `type(...) is bool` y `json.dumps(diagnostics)` sin excepción. Cubre exactamente el escenario que el audit identificó como faltante ("no usar únicamente fixtures ya saneados").

**Test B — persistence E2E** (`execution/src/test_score_store.py`, sección H nueva):
- Pasa un `numpy.bool_(True)`/`numpy.int64(7)` **reales** (no simulados con `bool`/`int` de Python) a `score_store.record()`, exactamente como lo haría `bot.py` si el fix del productor fallara. Verifica: `record()` no lanza (defensa en profundidad activa), el valor releído con `load_all()` es `bool`/`int` **nativo** de Python, y la línea escrita en disco es JSON válido de verdad (releída con `json.loads()` directamente del archivo, no solo confiando en que `load_all()` "arregle" algo en memoria).

**Test C — persistence failure isolation** (`execution/src/test_signal_quality_behavior_invariance.py`, escenario D nuevo):
- Monkeypatchea `score_store.record` para lanzar exactamente `TypeError('Object of type bool is not JSON serializable')` (el mismo mensaje que en producción) y ejecuta `LiveExecutionBot.process_closed_bar()` con una señal real armada (mismo harness `FakeMT5` que los escenarios A/B ya existentes). Verifica: se coloca exactamente 1 orden, `process_closed_bar()` **no propaga** la excepción, el request a `order_send()` es **idéntico** al escenario normal (A), y `self._last_processed_time` avanza correctamente pese al fallo de persistencia.

**Test D — behavior invariance**: ya cubierto por el escenario C de `test_signal_quality_behavior_invariance.py` (comparación campo-por-campo del request completo a `order_send()` entre A y D) — sin diferencias.

## 14. Reprocessing-bar finding

Cerrado por el aislamiento de la sección 6: con `score_store.record()` envuelto en su propio `try/except`, `self._last_processed_time` **siempre** avanza al final de `process_closed_bar()`, sin importar si la persistencia tuvo éxito — eliminando la posibilidad de que una barra ya procesada (orden ya colocada) se reprocese por culpa de un fallo puramente observacional. Verificado explícitamente (Test C, `self._last_processed_time == 1_700_000_000 + 32*300` tras forzar el fallo). No se rediseñó el lifecycle de procesamiento de barras más allá de esto — sigue existiendo el caso general (una excepción en OTRA parte de `process_closed_bar()`, fuera de `score_store.record()`) que no fue tocado, tal como pedía el enunciado ("no ampliar silenciosamente BOT-051.6.3" / "documentarlo como follow-up separado si aplica" — no se encontró evidencia de que ese caso más general esté ocurriendo actualmente, a diferencia del caso específico de persistencia que sí tenía evidencia real de producción).

## 17. Remaining limitations

- El proceso en vivo del usuario (puerto 8000, corriendo desde `2026-09-23T13:23:55Z`, confirmado vía `GET /status` read-only durante esta tarea) **sigue ejecutando el código de ANTES de este fix** — un proceso Python de larga duración no recarga código en caliente. - `351931195`/`352047367` quedan como pérdida de evidencia OOS permanente (sección 13) — no hay acción de recuperación posible sin violar el principio de no fabricar snapshots retrospectivos.
- El caso general de "cualquier excepción en `process_closed_bar()` antes de la última línea" más allá de `score_store.record()` específicamente no fue auditado ni tocado (ver sección 14) — se identificó en `BOT-051.6.2` como observación secundaria, no como parte del alcance de este hotfix.
